I

The thing itself

What it is

AeriaLite plays Apple's aerial footage as your desktop wallpaper: the drone shots of coastlines and cities you see on an Apple TV, underneath your icons and windows. The same catalogue Aerial has shown for years, in a lighter shape. What makes it worth writing about is not that it does this, but how little of your machine and your disk it uses while doing it.

Analogy

Aerial is a cinema that opens when you leave the room. This is a window that was always going to be there, with something moving on the other side of it.

Technical

One borderless NSWindow per screen, one level above the desktop icon layer, hosting an AVSampleBufferDisplayLayer driven by an AVSampleBufferRenderSynchronizer. It replaces the idleassetsd and WallpaperVideoExtension path entirely, which keeps a managed asset store and a resident decoder with no exposed control over either. Aerial 4.x takes the other route: an App Extension hosted by macOS, with the wallpaper set through PaperSaver rather than drawn directly, plus overlays, weather, live cameras and four runtime dependencies that this has none of.

The three commands

One program does three jobs: it runs as the wallpaper, it converts video files into a form that plays cheaply and stores small, and it fetches Apple's list of available clips.

Analogy

A ground crew for one aircraft. Somebody keeps it flying, somebody refits it between flights, somebody keeps the list of destinations. Only the first of the three works continuously.

Technical

aerialite play is the agent and the no-argument default. aerialite prep is the transcoder, shelled out to as a subprocess so an encoder failure cannot take the agent with it. aerialite catalog imports Apple's macOS aerial manifest. main.swift dispatches on argv[1] and sets line buffering first, because launchd redirects stdout to a file where block buffering hides every line until the process dies.

II

Why it is small

Never holding a frame

A single frame of 4K video, once decoded, is about 24 megabytes. A video player normally holds several at once. AeriaLite holds none. It reads the compressed data, which is a few tens of kilobytes per frame, and hands it to the part of macOS that was going to decode it anyway. The finished pictures live in memory that belongs to the system.

Analogy

Think of the difference between carrying a folded map and carrying the landscape. The compressed frame is the folded map: small, and useless until something unfolds it. AeriaLite never unfolds it. It hands the folded map through a window to someone whose job is unfolding, and that person keeps the landscape on their own desk.

Technical

AVAssetReaderTrackOutput constructed with outputSettings: nil is the whole mechanism. Passthrough mode yields CMSampleBuffers carrying compressed samples; decode happens inside the display layer's own VideoToolbox session, against IOSurfaces the compositor already owns and which are charged to no process. The file stays on disk and is read through the unified buffer cache, where pages are purgeable. No display link is involved, so none of the clock-death behaviour that bites a window-tied CAMetalDisplayLink applies.

What that costs

Playing 2940x1912 video costs about 18 megabytes and one percent of a processor core. When a fullscreen app hides the desktop, the processor cost drops to zero. The memory number does not change if you add a hundred more clips, or make the cache bigger, or raise the resolution.

Technical

Memory is invariant to library size because exactly one AVAssetReader is open at a time, and 18 MB is close to framework baseline for an AppKit and AVFoundation process. The figure is phys_footprint, not RSS: RSS reads around 52 MB here and the difference is shared and file-backed pages counted against every process that touches them. Any memory claim quoting RSS for this kind of work is quoting the wrong number, which is also why the comparison table refuses to guess at Aerial's: nobody has run footprint against it.

What it keeps

Apple ships 152 clips and each master is about 145 megabytes, so holding the catalogue as delivered costs roughly 22 gigabytes. AeriaLite converts each clip as it arrives and puts a ceiling on everything else. A real library of 15 clips measures 711 megabytes.

Analogy

Shopping for the week rather than the year. The cupboard has a size, what does not fit does not come home, and the oldest thing in it goes first.

Technical

Downloads conform to 1080p under a 2.5 Mbps average cap and trim at 180 seconds. Storage is bitrate times duration and almost nothing else: halving the framerate shrinks a file 8%, not 50%, because the bitrate target binds first, and with a cap set the resolution stops affecting size at all. Streamed copies are evicted least-recently-used against a byte and count cap; persistent/ is never evicted and never counted against it.

Trimming saves disk and zero bytes on the wire. The whole master downloads before any trim happens, so a 60-second cap against a 137-second master still pulls all 145 MB and then discards 56% of it. Worse, short clips need replacing sooner, which takes sustained streaming cost from 8.5 Mbps to about 19. Trim for disk, and only on files being kept.

III

Arguing with the compositor

Living on every desktop

macOS lets you have several desktops and swipe between them. A wallpaper has to be on all of them. The obvious way to ask for that turns out to fight with the swipe animation, and the symptom is bizarre: instead of a missing wallpaper you get thrown onto a different desktop entirely.

Analogy

Telling someone "stand in every room" and "do not move" at the same time. During a moment when two rooms are both visible, there is no position that satisfies both instructions, so the building picks a room for them and drags you into it.

Technical

collectionBehavior is [.ignoresCycle] and nothing more. Space membership comes from the private CGSAddWindowsToSpaces, given every Space of type == 0; fullscreen Spaces are excluded so the wallpaper never covers a fullscreen app. Three flags were removed for the same reason in turn: .fullScreenNone took a fullscreen cycle from 4 space changes to 11, .stationary threw the desktop rightward on an adjacent swipe, and .canJoinAllSpaces keeps one window and moves it to whichever Space became current, so mid-swipe the destination has nothing to composite.

Registration must be renewed after every orderFront, because ordering out drops it and a window belonging to no Space never appears. It must not run on a space change, because mutating membership during a transition drags the active Space exactly as the flags did.

Knowing when nobody looks

There is no point decoding video that a fullscreen app is covering. AeriaLite asks the window server whether its own window is visible, and stops when it is not. Finding a question the system would answer honestly took three attempts.

Analogy

Asking "am I on stage?" rather than "is the curtain down?" The first has one answer. The second depends on which curtain, and the theatre will happily describe a curtain that does not reach the floor.

Technical

Coverage.isVisible reads kCGWindowIsOnscreen for AeriaLite's own window. Two earlier approaches failed: NSWindow.occlusionState reports raw 8192 with .visible never set below normal window level and emits no notification; and testing whether a layer-0 window contains CGDisplayBounds never matches, because a real fullscreen window measures (0, 33, 1470, 923) against display bounds of (0, 0, 1470, 956).

The query is a synchronous IPC into WindowServer, which is also the process compositing the video, so it runs off the main thread. Gating is asymmetric: becoming visible applies at once, becoming hidden waits 0.75s behind a generation counter, because a window animating to full size reports not-covering for a beat.

IV

The pipeline

Play now, improve later

Apple's clips arrive as very large files. Converting one into something cheap to play takes minutes. Rather than making you wait, AeriaLite plays the large file immediately and swaps in the converted version later, at a moment when the picture was going to change anyway.

Analogy

A restaurant serving bread while the meal cooks. Swapping plates mid-mouthful would be worse than the wait, so the exchange happens between courses and nobody notices it happened.

Technical

A fetch lands the master in about 1.5 seconds, writes it into the catalogue, and pushes it into the playlist immediately. conform rewrites the same path, and since every clip is re-read from disk when it comes round, the encoded version takes over at a loop or track change. Forcing the swap mid-clip was built and removed: it flushed the sample queue and rewound up to a GOP, because a passthrough reader cannot begin mid-GOP and timeRange falls back to the preceding sync sample.

Why encoding takes minutes

Apple's newer clips run at 240 frames per second, eight times normal video. Converting two minutes of that means processing the same number of frames as nine minutes of ordinary footage. The encoder is not slow; there is simply a great deal of it.

Analogy

Copying a book by hand is not slow because your writing is slow. It is slow because of how many words there are. Asking for fewer words is the only lever that matters.

Technical

Measured against a 137s master of 32,865 frames, encoded to 2940x1912. Decode is an irreducible floor of roughly 116s: every source frame must be decoded even when it is about to be discarded, because inter-frame prediction means you cannot skip to frame N without the frames before it. Encode throughput is about 78 frames per second at that size, and cost is linear in output pixels; the scaler itself is free, measured at 1.4% over feeding it native directly.

Only framesKept: 0.25 finishes ahead of playback. Conforms run strictly one at a time at background quality of service: three concurrent hardware encodes contend for the same media engine, and the contention is visible as dropped frames.
